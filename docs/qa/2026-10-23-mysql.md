## 3. Cách kiểm tra rollback và mất kết nối

- Tạo trigger lỗi **trong database thử** tại bước ghi lượt đặt thiết bị. Lúc đó INSERT lịch đã đi trước trong cùng giao dịch. API trả 503; truy vấn SQL xác nhận không còn lịch vừa thử ghi và snapshot không đổi. Bỏ trigger rồi ghi lại thành công.
- Giữ khóa snapshot từ một connection kiểm thử, gửi yêu cầu từ hai tiến trình web. Hai yêu cầu phải chờ; sau khi thả khóa, một yêu cầu được ghi và yêu cầu còn lại nhận xung đột 409.
- Giữ khóa rồi ngắt đúng connection ứng dụng đang chờ trong database thử. API trả 503; snapshot không đổi; yêu cầu tiếp theo lấy kết nối mới và ghi thành công. Không dừng dịch vụ MySQL hay ngắt connection của database đang sử dụng.

## 4. Dữ liệu và dọn dẹp

- DDL/DML của bộ kiểm thử chỉ nhắm tới các database do chính lượt chạy tạo. Không chọn `DB_NAME` của người dùng làm đích kiểm thử.
- Cả **4 database thử đã được xóa** sau lượt chạy; truy vấn metadata xác nhận không còn các tên đó.
- Hash SHA-256 của `data/web-state.json` **không đổi** so với trước kiểm thử. Web cổng 8090 vẫn hoạt động, `storage=file`, revision 15 tại thời điểm kiểm tra.
- Mật khẩu MySQL chỉ được truyền qua môi trường tiến trình, không có trong test source hoặc báo cáo. Tài khoản ứng dụng trong test dùng mật khẩu ngẫu nhiên, độc lập dữ liệu người dùng.
- Lượt này không đổi cấu hình chạy, mật khẩu ứng dụng hay dữ liệu của web 8090. Cũng không áp dụng schema/migration vào database nghiệp vụ hiện hữu.

### Bản sao dữ liệu hiện tại

Đã nạp bản sao `data/web-state.json` vào database thử thứ tư, khởi động bộ chạy Node với MySQL và đối chiếu snapshot/projection. Kết quả giữ đủ:

| Dữ liệu | Số lượng |
| --- | --- |
| Phòng | 12 |
| Tài khoản | 30 |
| Thiết bị | 72 |
| Lịch họp | 169 |
| Lượt đặt thiết bị | 156 |

Snapshot và credentials được giữ nguyên về nội dung; file nguồn không đổi. MySQL JSON có thể sắp xếp lại thứ tự khóa object, nên phép so sánh nội dung không phụ thuộc thứ tự khóa. Không xuất nội dung credentials hoặc dữ liệu cá nhân vào báo cáo.

## 5. Chạy lại

Tại thư mục gốc dự án, cài dependency bằng `npm ci`, sau đó dùng PowerShell:

```powershell
$env:DB_HOST = '127.0.0.1'
$env:DB_PORT = '3306'
$env:DB_USERNAME = 'root'
$mysqlQaSecret = Read-Host 'Mật khẩu MySQL' -AsSecureString
try {
    $env:DB_PASSWORD = [System.Net.NetworkCredential]::new('', $mysqlQaSecret).Password
    npm run test:mysql
} finally {
    Remove-Item Env:DB_PASSWORD -ErrorAction SilentlyContinue
    $mysqlQaSecret.Dispose()
}
```

Tài khoản thử cần quyền tạo/xóa database, tạo bảng/trigger, đọc/ghi và xem/ngắt các connection kiểm thử của nó. Bộ test chỉ cho phép tạo/xóa các database tên sinh tự động của chính lượt chạy; không sử dụng `DB_NAME` có sẵn. `npm test` vẫn là bộ hồi quy thông thường và không tự kết nối MySQL.

Để kiểm tra thêm bản sao một file state đang có, đặt `MYSQL_QA_STATE_FILE` thành đường dẫn tới file đó trước khi chạy; bộ test chỉ đọc file nguồn và tạo database thử thứ tư, sau đó dọn sạch. Bỏ biến này khi chỉ muốn kiểm tra dữ liệu mẫu.

Có thể đặt `MYSQL_QA_REPORT` thành đường dẫn tới tệp trong một thư mục đã tồn tại để lưu kết quả JSON. Không cần lưu mật khẩu trong `.env`; bộ nạp cấu hình hiện không tự đọc `.env`.
